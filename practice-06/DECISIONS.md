# Практическая №6 — решения и объяснения

**Решение 1.** Все маршруты собраны в `ApprovalService.route` и проверяются от самого строгого к общему: персональные данные → HIGH → сумма от 500 000 → срочность → STANDARD. Это не позволяет обычному быстрому согласованию обойти требования безопасности.

**Решение 2.** Для условного варианта №3 параметр «20» трактуется как предел **20 000 денежных единиц** для FAST_TRACK; точную формулировку следует уточнить у преподавателя. Порог вынесен в одну константу `FAST_TRACK_LIMIT`.

## Разбор ошибки из задания

`if (urgent) return FAST_TRACK; if (containsPersonalData) return SECURITY_REVIEW;` — неверный порядок. Срочная заявка с персональными данными должна попасть на `SECURITY_REVIEW`, поэтому это условие идёт первым.

## Собственные формулировки

1. Неправильный ввод `true/false` проверяется в `Main.readBoolean`, отрицательная сумма и отсутствующий риск — в `ApprovalService.route`.
2. Ключевой бизнес-метод — `ApprovalService.route`: именно он выбирает результат по приоритетам.
3. Ветви Activity-диаграммы повторяют последовательность `if` в `route`.
4. Изменение предела срочной заявки должно затронуть только `FAST_TRACK_LIMIT` и проверки границы, без переписывания меню.
