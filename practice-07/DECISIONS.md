# Практическая №7 — решения и объяснения

**Решение 1.** Поля `EquipmentOrder.items` и `confirmed` — `private`, доступ к позициям через `List.copyOf(items)`, сами позиции и товары неизменяемые. Таким образом, нельзя тайно изменить уже подтверждённый заказ через ссылку на список.

**Решение 2.** Стоимость каждый раз вычисляется методом `calculateTotal`, а не хранится в изменяемом поле. Для цены используется `BigDecimal`, чтобы избежать ошибок округления `double`. Совпадение товаров определяется по `id`, но при конфликте названия/цены ввод отклоняется.

Для условного варианта №3 число «20» трактуется как верхний предел **суммарного количества при объединении повторной позиции**. Обычная новая строка допускает 1..100 товаров. Константа `MAX_MERGED_QUANTITY` находится в `EquipmentOrder`; точную трактовку необходимо уточнить.

## Ошибка из задания

`public List<OrderItem> getItems() { return items; }` отдаёт вызывающему коду изменяемую внутреннюю коллекцию. Так можно добавить/удалить позицию после `confirm`, обойдя защиту. Исправление: `return List.copyOf(items);`, а `OrderItem` сделать неизменяемым.

## Собственные формулировки

1. Главная защита входных данных — конструкторы `Product` и `OrderItem`: проверяют ID, название, цену и количество ещё до помещения в заказ.
2. `EquipmentOrder` хранит бизнес-инварианты уникальности товара, запрета изменения подтверждённого заказа и слияния позиций; `OrderService` связывает сценарии с интерфейсом.
3. На Activity-диаграмме ветка «есть позиция с таким ID?» соответствует циклу в `addProduct`, а «подтверждён?» — `ensureEditable`.
4. Лимит объединения можно изменить одной константой `MAX_MERGED_QUANTITY` и парой ожидаемых значений в тестах, не затрагивая пользовательское меню.
